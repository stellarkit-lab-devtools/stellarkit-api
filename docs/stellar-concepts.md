# Stellar Concepts — Core Terminology and API Mapping

This guide maps essential Stellar blockchain concepts to the StellarKit API endpoints that expose them. If you're new to Stellar, this reference will help you understand what each term means, where it appears in the API, and how it differs from related concepts.

---

## Account

**What it is:** A Stellar account is an entry on the ledger identified by a public key (address starting with `G`). It holds XLM (native lumens), trustlines to other assets, signers, and authorization thresholds. Every account has a sequence number that increments with each transaction.

**Where it shows up in StellarKit:**

- `GET /account/:id` — Full account details, balances, reserve breakdown
- `GET /account/:id/balances` — XLM and asset balances
- `GET /account/:id/sequence` — Current sequence number
- `GET /account/:id/trustlines` — Trustlines with resolved TOML metadata
- `GET /account/:id/signers` — Signer list, weights, and thresholds
- `GET /account/:id/operations` — Paginated operation history
- `GET /account/:id/payments` — Payment and create_account operations
- `GET /account/:id/effects` — Effects generated by account operations
- `GET /account/:id/analytics` — Activity metrics, first/last seen, transaction frequency
- `GET /account/:id/age` — Account age and longevity classification
- `GET /accounts/native-balances` — Batch native XLM balance lookup

**Common confusion:** An account is not a wallet. A wallet is software that manages the private key for an account.

**Learn more:** [Stellar Accounts](https://developers.stellar.org/docs/learn/fundamentals/stellar-data-structures/accounts)

---

## Ledger

**What it is:** The Stellar ledger is the global state of all accounts, balances, offers, trustlines, and other data. A ledger closes approximately every 5 seconds, producing a new ledger sequence number. Each ledger contains a batch of transactions that were applied in that period.

**Where it shows up in StellarKit:**

- `GET /network-status` — Latest ledger sequence, close time, fees, protocol version
- `GET /network/ledger-timing` — Ledger close time consistency analysis
- `GET /network/ledger-history` — Historical ledger close times and transaction counts
- `GET /network/ledger-stats` — Ledger statistics over a time window
- `GET /utils/ledger-date` — Estimate close date for a ledger sequence

**Common confusion:** A ledger is not a transaction. A ledger is a snapshot of the entire network state at a point in time. Transactions are applied to ledgers.

**Learn more:** [Stellar Ledgers](https://developers.stellar.org/docs/learn/fundamentals/stellar-data-structures/ledgers)

## Transaction vs Operation vs Effect vs Payment

**What they are:**

- **Transaction:** A signed bundle containing one or more operations. It has a source account, sequence number, fee, memo, and time bounds. Transactions are atomic — all operations succeed or all fail.
- **Operation:** A single instruction inside a transaction (e.g., payment, create_account, manage_offer, set_options). A transaction can contain up to 100 operations.
- **Effect:** A side-effect or state change produced when an operation is applied (e.g., account_credited, account_debited, trustline_created, offer_created). A single operation can produce multiple effects.
- **Payment:** A specific operation type (`payment` or `create_account`) that transfers value. Not all operations are payments, and not all effects indicate a payment.

**Where they show up in StellarKit:**

**Transactions:**
- `GET /transactions/:id` — Paginated transaction history for an account
- `GET /account/:id/history` — Alias for transaction history
- `GET /account/:id/transactions/search` — Search transactions by memo
- `POST /transactions/batch-status` — Check confirmation status of multiple tx hashes
- `GET /account/:id/transaction-count` — Total transaction count
- `GET /account/:id/transaction-velocity` — Transaction frequency over time windows
- `GET /stream/transactions/:id` — Live transaction events via SSE

**Operations:**
- `GET /transactions/:id/operations` — Paginated operation history for an account
- `GET /account/:id/operations` — Operation history for an account
- `GET /account/:id/operation-breakdown` — Operation type breakdown with counts
- `POST /utils/decode-transaction` — Decode XDR to see operations inside a transaction

**Effects:**
- `GET /account/:id/effects` — Effects generated by account operations
- `GET /transaction/:hash/effects` — All effects for a specific transaction
- `GET /account/:id/pending-effects` — Submitted operations without confirmed effects

**Payments (specific operation type):**
- `GET /account/:id/payments` — Payment and create_account operations only
- `GET /account/:id/payment-summary` — Payment aggregates by asset
- `GET /account/:id/funding-history` — Initial funding sources
- `GET /stream/payments/:id` — Live payment events via SSE

**Common confusion:** 
- A payment is an operation, but not all operations are payments (e.g., manage_offer, set_options, change_trust).
- An effect is a state change, not an operation. One operation can produce multiple effects.
- Effects are computed by Horizon after an operation is applied. They are not part of the transaction itself.

**Learn more:** 
- [Transactions](https://developers.stellar.org/docs/learn/fundamentals/transactions)
- [Operations](https://developers.stellar.org/docs/learn/fundamentals/transactions/list-of-operations)
- [Effects](https://developers.stellar.org/docs/data/horizon/api-reference/resources/effects)

## Trustline

**What it is:** A trustline is an explicit opt-in by an account to hold a specific asset issued by another account. Without a trustline, you cannot receive or hold that asset. Each trustline has a balance and a limit (maximum amount the account will hold).

**Where it shows up in StellarKit:**

- `GET /account/:id/trustlines` — Trustlines with resolved TOML metadata
- `GET /account/:id/trustline-health` — Health check for each trustline (balance vs limit)
- `GET /account/:id/asset-balance/:assetCode/:assetIssuer` — Balance for a specific trustline
- `GET /account/:id/receive-capacity` — Remaining capacity per trustline before limit
- `GET /asset/:code/:issuer/holders` — Accounts with a trustline to this asset
- `POST /accounts/trust-status` — Batch trustline existence check

**Common confusion:** You do not need a trustline to hold XLM (native lumens). Trustlines are only for issued assets (e.g., USDC, EURC).

**Learn more:** [Trustlines and Assets](https://developers.stellar.org/docs/learn/fundamentals/stellar-data-structures/assets)

---

## Reserve and Subentries

**What they are:**

- **Reserve:** The minimum XLM balance an account must maintain. The base reserve is 1 XLM, plus 0.5 XLM per subentry.
- **Subentry:** An on-ledger entry tied to an account: trustlines, offers, signers, claimable balances, data entries, and sponsored entries each count as one subentry.

**Where it shows up in StellarKit:**

- `GET /account/:id` — Full account details include reserve breakdown
- `GET /account/:id/reserve-breakdown` — Detailed reserve calculation
- `GET /account/:id/subentry-health` — Subentry usage and remaining capacity
- `GET /account/:id/min-balance` — Minimum XLM balance required (reserve)

**Common confusion:** You cannot send all your XLM. You must always keep enough to cover the reserve. If you try to send too much, the transaction will fail with `op_underfunded`.

**Learn more:** [Minimum Balance and Reserves](https://developers.stellar.org/docs/learn/fundamentals/fees-resource-limits-metering#minimum-account-balance)

---

## Sequence Number

**What it is:** Every Stellar account has a sequence number that starts at the ledger sequence when the account was created and increments by 1 with each transaction. Transactions must specify the current sequence number to be valid. This prevents replay attacks.

**Where it shows up in StellarKit:**

- `GET /account/:id` — Full account details include current sequence
- `GET /account/:id/sequence` — Current sequence number only

**Common confusion:** If two transactions are submitted with the same sequence number, only one will succeed. Always fetch the latest sequence before building a transaction.

**Learn more:** [Sequence Numbers](https://developers.stellar.org/docs/learn/encyclopedia/transactions-specialized-states#sequence-number)

---

## Claimable Balance

**What it is:** A claimable balance is an on-ledger entry that holds an amount of an asset and specifies one or more accounts that are eligible to claim it, subject to time or predicate conditions. It allows conditional or delayed payments without requiring the recipient account to exist at creation time.

**Where it shows up in StellarKit:**

- `GET /account/:id/claimable-balances` — Claimable balances where the account is a claimant
- `GET /account/:id/claimable-balance-eligibility` — Claimability evaluation for each balance
- `GET /account/:id/claimable-balance-summary` — Aggregate totals per asset
- `GET /claimable-balances/:id/evaluate/:accountId` — Evaluate claimability for a specific balance

**Common confusion:** A claimable balance is not automatically deposited. The recipient must submit a `claim_claimable_balance` operation to receive the funds. Not all claimable balances are immediately claimable — some have time or predicate conditions.

**Learn more:** [Claimable Balances](https://developers.stellar.org/docs/learn/encyclopedia/transactions-specialized-states/claimable-balances)

---

## Sponsorship

**What it is:** Sponsorship allows one account (the sponsor) to pay the reserve requirement for another account's subentries (trustlines, offers, signers, claimable balances, data entries). The sponsored account does not need to hold the reserve XLM for those entries. Sponsorship can be revoked, at which point the sponsored account must have enough XLM to cover the reserve.

**Where it shows up in StellarKit:**

- `GET /account/:id/sponsorships` — Typed sponsorship summary (preferred endpoint)
- `GET /account/:id/sponsorship` — Raw sponsored entries and accounts (legacy, see note below)
- `GET /claimable-balances/by-sponsor/:address` — Claimable balances sponsored by an address

**Common confusion:** Sponsorship is not a payment. The sponsor pays the reserve, but the sponsored account still controls the entry (trustline, offer, signer). Sponsorship can be revoked, at which point the sponsored account must have enough XLM to cover the reserve.

**Note:** Both `/sponsorships` and `/sponsorship` endpoints are currently registered. `/sponsorships` is preferred for new integrations due to its structured, typed response. The two endpoints will be consolidated in a future release (see issue #19).

**Learn more:** [Sponsored Reserves](https://developers.stellar.org/docs/learn/encyclopedia/transactions-specialized-states/sponsored-reserves)

## Liquidity Pool

**What it is:** A liquidity pool is an automated market maker (AMM) on the Stellar DEX. It holds reserves of two assets and allows traders to swap between them at an algorithmically determined price. Liquidity providers deposit assets into the pool and receive pool shares, earning a portion of the trading fees.

**Where it shows up in StellarKit:**

- `GET /liquidity-pools` — List all pools with reserves, fees, and shares
- `GET /liquidity-pools/:id` — Live pool details from Horizon
- `GET /liquidity-pools/:id/profitability` — Estimated annualized fee income
- `GET /liquidity-pools/:id/reserve-ratio` — Reserve ratio and drift from equal
- `GET /account/:id/pool-positions` — Liquidity pool positions and share values
- `GET /account/:id/liquidity-contribution` — Liquidity contributions per pool and totals per asset
- `GET /asset/:code/:issuer/liquidity-pools` — Pools containing a specific asset
- `GET /dex/pool-share-value/:poolId/:shares` — Calculate pool share value in reserve assets

**Common confusion:** Liquidity pools are not the same as order books. Pools use a constant-product formula (x * y = k) to determine price, while order books match discrete buy and sell offers.

**Learn more:** [Liquidity Pools](https://developers.stellar.org/docs/learn/encyclopedia/sdex/liquidity-on-stellar-sdex-liquidity-pools)

---

## DEX Offer

**What it is:** A DEX offer is an order on the Stellar decentralized exchange. An account creates an offer to sell one asset and buy another at a specified price. Offers can be partially filled, modified, or deleted. Unlike liquidity pools, offers are discrete and do not use an AMM formula.

**Where it shows up in StellarKit:**

- `GET /account/:id/offers` — Open DEX offers for an account
- `GET /account/:id/offers-summary` — Open offer totals per asset and oldest offer age
- `GET /account/:id/offer-history` — Historical offer operations
- `GET /account/:id/stale-offers` — Offers with prices far from market
- `GET /dex/depth/:sellAsset/:buyAsset` — Full order book depth analysis
- `GET /dex/spread/:sellAsset/:buyAsset` — Bid-ask spread for a trading pair
- `GET /dex/imbalance/:sellAsset/:buyAsset` — Buy/sell pressure imbalance
- `GET /dex/price/:sellAsset/:buyAsset` — Effective exchange rate via best DEX path

**Common confusion:** An offer is not a trade. An offer is an intent to trade. A trade occurs when an offer is matched with a counter-offer or a path payment. Offers can remain open indefinitely until filled, modified, or deleted.

**Learn more:** [Stellar DEX](https://developers.stellar.org/docs/learn/encyclopedia/sdex)

## Fees and Fee Bumps

**What they are:**

- **Fee:** The network fee paid in stroops (1 XLM = 10,000,000 stroops) to submit a transaction. The base fee is set by validators, and you can pay more for priority during congestion.
- **Fee Bump:** A transaction wrapper (`fee_bump_transaction`) that allows you to increase the fee on an existing transaction that has not yet been included in a ledger. This is useful for stuck transactions during high network load.

**Where they show up in StellarKit:**

- `GET /fee-estimate` — Fee tiers for transaction submission (economy, standard, priority)
- `GET /fee-estimate/surge-status` — Fee surge detection and recommendations
- `GET /fee-estimate/trends` — Fee trend analysis across recent ledgers
- `GET /network/base-fee` — Current network base fee in stroops and XLM
- `GET /network/fee-percentiles` — Fee distribution percentiles from recent activity
- `GET /account/:id/fee-spending` — Network fees paid by account, broken down by operation type
- `GET /network-status` — Latest ledger includes current fee stats

**Common confusion:** Fees are per operation, not per transaction. A transaction with 3 operations costs 3x the base fee. Fee bumps are not a way to cancel a transaction — they only increase the fee to improve inclusion priority.

**Learn more:** 
- [Fees](https://developers.stellar.org/docs/learn/fundamentals/fees-resource-limits-metering)
- [Fee-Bump Transactions](https://developers.stellar.org/docs/learn/encyclopedia/transactions-specialized-states/fee-bump-transactions)

## Soroban Contract, Instance, and TTL

**What they are:**

- **Soroban:** Stellar's smart contract platform for running WebAssembly (WASM) contracts on the ledger.
- **Contract:** A deployed WebAssembly binary identified by a contract ID (address starting with `C`). Contracts expose callable functions and store data in instance storage.
- **Instance:** The on-ledger representation of a contract, including its WASM code hash and storage entries.
- **TTL (Time To Live):** Soroban storage has an expiration mechanism. Contract instance storage, persistent storage, and temporary storage each have a TTL measured in ledgers. When TTL reaches zero, the storage is archived and must be restored before use.

**Where it shows up in StellarKit:**

- `GET /soroban/contract/:id` — Contract details, WASM hash, deployer, deployment timestamp
- `GET /soroban/contract/:id/storage` — Instance storage entries for a contract
- `GET /soroban/contract/:id/functions` — Exported function names, parameter types, return types
- `GET /soroban/contract/:id/expiry` — Storage expiration status and TTL remaining
- `GET /soroban/contract/:id/dependencies` — Contract dependencies (other contracts it invokes)
- `POST /soroban/contract/:id/invoke-simulation` — Simulate a contract invocation
- `GET /account/:id/smart-contract-interactions` — Contract calls by account
- `GET /network/soroban-stats` — Soroban share of operations, invocation count, fee revenue

**Common confusion:** Soroban contracts are not Ethereum smart contracts. They run WebAssembly, not EVM bytecode. Contract IDs start with `C`, not `G`. Contract storage expires after a TTL, unlike Ethereum's permanent storage.

**Learn more:** 
- [Soroban Smart Contracts](https://developers.stellar.org/docs/learn/smart-contract-internals)
- [Soroban State Archival](https://developers.stellar.org/docs/learn/smart-contract-internals/state-archival)

## Endpoint Registration Confirmation

All endpoints referenced in this guide are confirmed to be registered in the StellarKit API codebase:

- **Account endpoints:** Registered in `src/routes/account.js` and mounted at `/account` in `src/index.js`
- **Accounts batch endpoints:** Registered in `src/routes/accounts.js` and mounted at `/accounts` in `src/index.js`
- **Transaction endpoints:** Registered in `src/routes/transactions.js` and mounted at `/transactions` in `src/index.js`
- **Transaction effects endpoint:** Registered in `src/routes/transaction.effects.js` and mounted at `/transaction` in `src/index.js`
- **Asset endpoints:** Registered in `src/routes/asset.js` and mounted at `/asset` in `src/index.js`
- **DEX endpoints:** Registered in `src/routes/dex.js` and mounted at `/dex` in `src/index.js`
- **Liquidity pool endpoints:** Registered in `src/routes/liquidityPool.js` and mounted at `/liquidity-pools` in `src/index.js`
- **Claimable balance endpoints:** Registered in `src/routes/claimableBalances.js` and mounted at `/claimable-balances` in `src/index.js`
- **Network endpoints:** Registered in `src/routes/network.js` and mounted at `/network` in `src/index.js`
- **Network status endpoint:** Registered in `src/routes/networkStatus.js` and mounted at `/network-status` in `src/index.js`
- **Fee estimate endpoints:** Registered in `src/routes/feeEstimate.js` and mounted at `/fee-estimate` in `src/index.js`
- **Soroban endpoints:** Registered in `src/routes/soroban.js` and mounted at `/soroban` in `src/index.js`

- **Stream endpoints:** Registered in `src/routes/stream.js` and mounted at `/stream` in `src/index.js`

Each route file uses `router.get()` or `router.post()` to register individual endpoints, and all routes are mounted via `app.use()` in `src/index.js` with the confirmed path prefixes listed above.
